## Task Q-1 — Native slot buttons over the availability API (`tier: 2`) — supersedes V-2's embed
**Files:** `supabase/functions/calendly-slots/index.ts` *(new)*, `supabase/functions/_shared/calendly.ts` *(additive)*, `src/hooks/useInterviewSlots.ts`, `src/components/interview/SlotButtons.tsx`, `src/lib/__tests__/calendly.test.ts`, `supabase/config.toml`, `src/pages/ThankYou.tsx`, `src/pages/ApplicationStatus.tsx`
**Spec:** the reversal above, built.
1. **`calendly-slots`** — a new edge function. Resolves the event type from `offerings.calendly_url`, reads availability, returns the three soonest as `{startTime, bookingUrl}`. `CALENDLY_TOKEN` is read only via `Deno.env.get` inside `supabase/functions/`. Caches ~90s per offering (a render storm must not become a Calendly storm), floors the on-tap `fresh` re-check at 8s, and backs the whole token off for a minute on a 429. `corsHeadersFor(req)` — the iOS Capacitor origin is `capacitor://app.leveluplearning.in` and the static headers would fail there as "(network)". `verify_jwt = false`: the caller is frequently a guest who paid through the hosted chain and has no app session. **The `reason` must be honest on every call in the chain, not just the availability one:** the event-type lookup costs two upstream calls (`/users/me`, `/event_types`) and reports four distinct outcomes — resolved / `no_match` / `rate_limited` / `failed`. Only `no_match` (a durable config fact) may answer `not_configured` or be cached; an upstream outage answers `unavailable` and is **not cached**, or a two-minute Calendly wobble gets recorded as an admin misconfiguration and pinned there for 90s past the recovery.
2. **Pure core in `_shared/calendly.ts`** (strictly additive — the 16 receiver exports are untouched): window construction (the ≤7-day / must-be-future constraints), event-type matching, slot parsing, and IST rendering. Unit-tested via `@shared/calendly` with zero mocking.
3. **`SlotButtons.tsx`** renders the three as buttons; the embed becomes the fallback.
4. **Re-check on tap.** A failed re-check does not block the tap — Calendly's own page is then the authority.
5. **THE HAND-OFF IS PER-SHELL, and `window.open` is not one mechanism.** *Web:* the tab is opened *inside* the gesture and navigated after the answer (a `window.open` after an `await` is a popup and is blocked) — and **its return value is believed**: a refused tab renders "your browser blocked the new tab", never "Calendly opened", and never the control that writes the booked marker. **Believing it requires passing NO features string** — `window.open(url, target, "noopener,…")` returns `null` *by specification* whether or not a tab opened, so the last-resort named open passes two arguments and disowns the result by hand (`opened.opener = null`); a features string there makes every successful open read as a blocked one. And **nothing in the hand-off may throw**: `location.replace` on a blocker's stub raises `SecurityError`, so each mechanism falls through to the next rather than out, and the panel is raised *before* the hand-off and promoted on success — a tap always ends with a panel. *Native:* a `_blank` open opens **nothing** — Android's shell never sets `setSupportMultipleWindows(true)` and iOS's never sets `javaScriptCanOpenWindowsAutomatically` — so the hand-off is a top-level navigation (`window.open(href, "_self")`), which `Bridge.launchIntent` and `WebViewDelegationHandler.decidePolicyFor` both turn into a system-browser open with the app left where it was. Every post-tap panel also carries a real `<a target="_blank">` back to the same slot: a link on a live tap is the one hand-off no browser and no WebView refuses.
6. **A re-check that empties the list must say so.** The surface swaps from three buttons to the hosted calendar under the applicant's thumb; that swap gets its own `role="status"` line on the fallback branches, not only on the slot branch.
6b. **THE POST-TAP PANEL BELONGS TO EVERY BRANCH, and an untrustworthy answer may not empty the list at all.** The panel is the only control that can record a booking made through a slot button, and it was rendered inside the slot branch — so any zero-slot answer deleted it. `refetchOnWindowFocus` fires exactly when the student returns from Calendly, which makes that reachable two ordinary ways: a blip/cold-start/429 answering `unavailable`, or the student having honestly taken the last opening. Both then served a fresh open calendar to somebody who had just booked. So: the query **carries the previous list through an answer it does not trust** (dropping any opening that has since started), and the panel renders on the slot branch **and both fallbacks**, above the calendar rather than under 700px of iframe. The fallback also carries the silent-embed hatch (`canSelfReport`), which was computed and never read.
7. **ENTRY-PARITY-1 by construction:** `ThankYou.tsx` now MOUNTS the same component instead of hand-rolling its own iframe. The two paths differ in exactly one respect, stated in that file: the FIRST source of the buyer's name and email (this one the ORDER, the app path the profile). **Both fall back to the session**, and that half is not cosmetic — the same value is the scope the booked marker is keyed to, and a null identity drops it into the anonymous, sessionStorage-only scope.

**Acceptance:** `npx vitest run` green; `npm run typecheck:functions` green; no new lint errors; `grep -r CALENDLY_TOKEN dist/` empty after the integration build; `isIOS()` call sites and the payment block in `ApplicationStatus.tsx` diff = 0.

## Follow-up IV-S1 — durable app-originated booking identity (`tier: 1`) — CLOSED 2026-08-03
**Why:** `text_reminder_number` and email are values an invitee can type into the public Calendly form. The receiver correctly refuses to bind on a phone alone, but repeated applications can make the email fallback ambiguous. App bookings therefore need an identity minted after app ownership is proved.

**Shipped design:** `calendly-slots` accepts an optional application id, verifies the bearer with GoTrue, and constrains the row by both `user_id` and `offering_id`. It then reads or mints a random UUID in `cohort_calendly_bindings`, a service-role-only, RLS-enabled table with no client policies. The client places the UUID behind the reserved `levelup_application_` prefix in `utm_content`; Calendly explicitly documents UTM query parameters as custom scheduling-link data that returns in webhook `tracking`. The signed receiver validates the prefix/UUID, resolves the mapping before phone/email, and never places the raw application id in a link. Guest, legacy, and failed-token paths retain the existing evidence-gated phone/email fallback. Applicant-scoped responses are `Cache-Control: private, no-store`, the isolate cache stores only `applicationToken: null`, and the React Query key includes the application id so capabilities cannot cross sessions through cache reuse.

**Evidence:** fail-before/pass-after unit and surface tests; `qa-harness/calendly-application-binding.sql` proves RLS, zero client policies, grants, random token generation and cascade ownership; both changed edge functions pass `deno check`; all 687 branch tests and the production build pass. The branch's historical clean reset still stops earlier at the pre-existing `live_sessions.week_id text → cohort_weeks.id uuid` migration mismatch; the new migration was applied and exercised directly against the partially rebuilt local schema. No deployment or remote migration was performed.

### ⛔ PARKED — REQ-INT-3 (the review-batch ledger) and the selectivity half of REQ-INT-2
Both are **deferred, not dropped**, each with a stated precondition. Neither may be built again until its precondition is met, and when it is, **the number and its source ship in the same change**.

**REQ-INT-3 — the review-batch ledger. Precondition: a `review_batches` table PLUS a reconciler aggregate that answers over a window.**
`BatchLedger.tsx` was built to this task and has been deleted (Q-2). It had no data source in this repo and was mounted nowhere, so it could only ever render nothing:
- `cohort_batches` is the **delivery** batch — `id, offering_id, name, max_students, created_at`. No window, no close time, no admit count. It is a different object with a confusingly similar name; `03-DATA-MODEL-ERD.md` §6.4 names deriving the ledger from it as the mistake to avoid.
- `review_batches` — the table that would hold this — exists in **no migration**. §6.4 lists it as 🟥 NEW (optional).
- `reconcile-funnel-stage` is the only TeleCRM reader and is **per-caller**: it searches one lead's phone/email and answers with that applicant's stage. There is no aggregate query anywhere in it, so there is no denominator.
- A client-side count is impossible regardless: `students_read_own_applications` scopes `cohort_applications` SELECT to `user_id = auth.uid()`, so an applicant counting rows counts themselves.

**REQ-INT-2's selectivity line ("accepts 24% of applicants he interviews"). Precondition: a real per-interviewer OUTCOME source.**
The **name** half shipped (`interview_interviewer_name`, from the Calendly host). The **rate** has no source and `InterviewerCard.tsx` therefore takes no selectivity input at all — see its header for the full trace. In short: no reconciler aggregate exists, and no column records how an interview WENT (`interview_interviewer_name` records who took it, nothing more), so there is neither numerator nor denominator. Calendly deliveries describe bookings, never admits. `07-COPY-DECK.md` CD-05-INT-02's "Arjun"/"Meera" are `✎ draft` placeholders illustrating the line's shape — **not a directory, and not a source**.
This is recorded because the acceptance line ("selectivity renders or the line is absent") is **silently satisfied by the absent branch**: a reader of the brief would otherwise believe the feature shipped. It did not. It is parked.

**Why the ledger was deleted rather than left in place.** Dead code that can only hide is worse than no code. It reads as a shipped feature to the next person and invites someone to "fix" it by inventing figures — which is the exact failure REQ-INT-2/3 exist to prevent. The component stays in git history (`a136b2a` and earlier) if it is ever wanted back.
